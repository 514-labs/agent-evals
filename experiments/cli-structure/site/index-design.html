A report on designing tools for AI agents

Shape the Tool.

Three hundred agent sessions, five command-line shapes, one surprise: the CLI your agent wants depends on how long it stays.

I
The hunch

Everyone said agents want flat CLIs.

The argument was simple. Agents have no mental model, so they can't navigate hierarchy. Show them every command in one place. Dump the whole surface flat. That's what a machine wants.

We believed it. We also doubted it. So we built five versions of the same command-line tool — from deeply nested to fully flat — and paid 300 Claude sessions to try them.

The five shapes shared one surface of forty commands. Only the arrangement changed. Deep hid everything under three-level namespaces. Atomic exposed every capability as its own top-level verb. Three in-between.

Six tasks. Ten repetitions each. Fresh containers, no configuration leakage. We measured tool calls, help reads, errors, cost, and preserved every trace.

II
What we saw

The ranking flipped.

On single tasks the flat shapes won, exactly as predicted. On sessions of five related tasks, the ranking reversed. The deeply nested CLI became the cheapest; the flat ones became the most expensive.

The agent teaches itself a CLI in six steps.
deep/combined/rep1

Five tasks in sequence. The agent guesses the first command wrong because it expects the flat form it has seen elsewhere. It reads help once. Then, without consulting help again, it correctly routes four more tasks across three different namespaces.

Claude20:37:10 moose data seed --source clickhouse://…

One help read amortized across five tasks. This is what the data means when we say agents like nested CLIs for sessions — not that they like nesting, but that nesting gives them something reusable.

Or it invents three verbs that don't exist.
atomic/b/rep5

The same task on the fully-flat CLI. The agent, given no hierarchy to constrain its guess, reaches for what sounds plausible. None of it works. This pattern replicated in 9 of 10 runs.

Claude— moose logs --filter error
Claude— moose logs | grep -i error
Claude— moose log --filter error
CLI— error: unknown command 'logs'.
Did you mean moose search-logs?
Claude— moose search-logs --help
Claude— moose search-logs error

Flat enumeration doesn't stop the agent from guessing verbs that don't exist. The English phrasing "search the logs" cues a verb with the word logs in it, and nothing in the surface rejects the cue until the error fires.

III
What to build

Match the shape to the session.

Not humans vs. agents. Not flat vs. nested. The real variable is how long the executor — any executor — sits in your tool before leaving.

If your tool is used in short bursts — health checks, one-off queries, status — flat is cheaper. The agent doesn't stay long enough to amortize any structural lesson. Positional layouts (moose logs error) are particularly efficient because a positional argument is a one-step disambiguation signal.

If your tool is used for orchestration — init, configure, seed, validate, deploy — nest it. The agent will pay the exploration cost once and reuse the namespace for every subsequent step. Deep's one help read bought the correct routing of five tasks.

And if you're tempted by the maximalist flat design where every capability is its own kebab-case verb at the top level — don't. It triples the error rate because it gives the agent unlimited lexical surface on which to guess.

The best of both worlds, though we are still validating, may be the shape git accidentally arrived at thirty years ago: nested underneath, with the five or seven most-common verbs surfaced as top-level aliases. We're testing it now.

Design recommendation

Nest the surface. Surface the shortcuts.

Below four related tasks per session, go flat. At or above four, go nested — and surface the five most-common verbs at the top level. Never ship one-flat-verb-per-capability. The agent will invent verbs you haven't written.
