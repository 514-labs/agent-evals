---
title: "Scoring"
description: "Five gates, strictly sequential. Efficiency breaks ties."
---

Scoring is deterministic -- no LLM-as-judge. Five gates, evaluated in order. Fail a gate, and nothing above it counts.

## Gates

| Gate | Name | One-liner |
|------|------|-----------|
| 1 | **Functional** | It runs |
| 2 | **Correct** | It produces right answers |
| 3 | **Robust** | It handles real-world conditions |
| 4 | **Performant** | It's fast enough |
| 5 | **Production** | You'd ship this |

Each gate checks two things:

1. **Core assertions** -- universal, binary pass/fail (e.g., `process_exits_clean`, `idempotent_rerun`)
2. **Scenario assertions** -- weighted points defined by the scenario author (e.g., `handles_nulls`, `query_under_200ms`)

A gate passes when all core assertions pass **and** scenario assertions hit the 80% threshold.

Production includes a shared deterministic hygiene floor before any scenario-specific ship checks:

- `uses_env_vars`
- `no_secrets_in_code`
- `output_line_count_reasonable`
- `output_line_count_disciplined`
- `no_dead_code_markers`
- `files_are_reasonably_sized`
- `no_debug_artifacts`
- `zero_compiler_errors`
- `zero_lint_errors`
- `has_type_safety`
- `functions_are_focused`
- `no_deep_nesting`

The file-size and total-line checks support scenario-level overrides through `scenario.json`:

- `productionChecks.maxExpectedLines`
- `productionChecks.maxFileLines`

Line-count scoring is intentionally stricter at the top gate:

- `output_line_count_disciplined` uses the exact scenario target.
- `output_line_count_reasonable` uses a 1.25x hard ceiling on that same target.

When a scenario does not override the thresholds, tier defaults apply:

| Tier | `maxExpectedLines` | `maxFileLines` |
|------|--------------------|----------------|
| `tier-1` | `200` | `250` |
| `tier-2` | `350` | `250` |
| `tier-3` | `500` | `250` |

## Efficiency

Wall clock time, agent steps, tokens used, and LLM API cost are tracked but scored separately. They break ties between agents at the same gate -- they never inflate or deflate the gate score itself.

When available, we preserve raw token buckets such as `inputTokens`, `outputTokens`, and cache-related token counts. If an agent CLI reports a dollar cost directly, we store that as `llmApiCostSource = "agent-reported"`. If a CLI only reports token counts, we derive `llmApiCostUsd` from the stored token buckets using published per-token pricing and mark it as `llmApiCostSource = "derived-from-published-pricing"`.

## Output

Two values drive the leaderboard:

| Field | Type | Purpose |
|-------|------|---------|
| `highest_gate` | integer 0--5 | Primary rank |
| `normalized_score` | float 0--1 | Fine-grained ordering within the reached gate band |

`normalized_score` is a gate-banded score:

- Each fully passed gate contributes its full `0.20` band.
- If a run fails a gate, it still lands inside that gate's band based on how many assertions passed in that gate.
- Core assertions count in that failed-gate fraction alongside scenario assertions.
- Blocked gates above the first failure contribute `0`.

Within each gate, `gates[gate].score` still records the raw scenario-assertion score for audit/debug detail. That field can stay high even when the gate fails on a core assertion; `normalized_score` is the leaderboard-safe version of progress.

## Assertion Log Sidecar

Rich per-assertion runtime logs are stored in a separate sidecar file, not in the main result JSON. This keeps scoring output lean while preserving audit evidence.

- Sidecar file name: `.assertion-log.json` (copied into audit bundles as `logs/assertion-log.json`)
- Manifest log entry id: `assertion_log`
- Shape: gate -> `{ core, scenario }` -> assertion name -> `{ passed, durationMs, message?, error?, details? }`

```json title="assertion-log.json"
{
  "functional": {
    "core": {
      "process_exits_clean": {
        "passed": true,
        "durationMs": 0,
        "message": "Agent process exited cleanly.",
        "details": { "exitCode": 0 }
      }
    },
    "scenario": {
      "target_table_exists": {
        "passed": true,
        "durationMs": 45,
        "message": "Target table exists.",
        "details": { "expected": 1, "actual": 1 }
      }
    }
  },
  "correct": { "core": {}, "scenario": {} },
  "robust": { "core": {}, "scenario": {} },
  "performant": { "core": {}, "scenario": {} },
  "production": { "core": {}, "scenario": {} }
}
```

The audit rubric panel uses this sidecar to show assertion-specific evidence (duration, message, thrown error, details JSON) for each assertion row.
