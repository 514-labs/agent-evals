---
title: "Calibrating and Maintaining Scenarios"
description: "Review results, adjust thresholds, and version changes to keep scenarios reliable over time."
---

A scenario is not finished when it merges. As agents improve and the benchmark grows, scenarios need periodic review to stay meaningful.

## Reviewing results

After a scenario has been run across multiple agents and models, look for patterns in the results:

- **Failure clusters**: if every agent fails the same assertion, the assertion may be too strict or the prompt may be missing critical context.
- **Universal passes**: if every agent passes every gate, the scenario may not be differentiating. Consider adding harder assertions or moving to a higher tier.
- **Flaky results**: if the same agent/model combination produces different scores across runs, the scenario has non-determinism. Check seed data, service startup order, and assertion timing.

## Adjusting thresholds

Performance and production gate assertions often include numeric thresholds (query latency, row counts, timing budgets). When adjusting these:

- Document the rationale for the change. "Relaxed from 100ms to 200ms because baseline hardware varies" is traceable. A silent threshold change is not.
- Test the new threshold against existing results before merging. A threshold change that retroactively flips pass/fail for published runs affects leaderboard interpretation.

## Versioning changes

Any change to a scenario that can alter its scoring output should be treated as a version change:

- Modified assertions (new checks, changed thresholds, removed checks)
- Changed seed data or init scripts
- Updated prompts

The benchmark tracks scenario versions through the `version` field in run metadata. When making breaking changes, update the version so that results from different versions are not compared directly.
