A DEC Bench evaluation runs every combination of four independent variables:

| Variable | What it is |
|----------|-----------|
| **Scenario** | The data engineering task: infrastructure, seed data, and success criteria |
| **Agent / Model** | The AI coding agent and the LLM behind it (Claude Code, Codex, Cursor) |
| **Harness** | The tools available to the agent (base-rt, classic-de, olap-for-swe) |
| **Persona** | The type of user giving instructions (baseline or informed) |

For each combination, the benchmark measures gate achievement (how far through the five quality gates the agent gets) and efficiency (wall-clock time, token usage, cost).

Adding a scenario means defining a new task that can be run across all agents, harnesses, and personas. As part of this, you define:

1. The scenario itself: infrastructure, seed data, and the problem statement
2. The prompts used by each persona
3. The assertions that prove gate achievement

Before creating a new scenario, check whether a similar one already exists. The [scenarios directory](https://github.com/514-labs/agent-evals/tree/main/scenarios) contains all current scenarios. Use an LLM to search through them if you are unsure.

This guide covers:

1. Creating and testing a new scenario locally
2. Publishing it to DEC Bench via pull request

## Prerequisites

- The `dec-bench` CLI installed (see [Quickstart](/docs))
- [Docker](https://docs.docker.com/get-started/get-docker/) installed and running
- Local clone of the [repository](https://github.com/514-labs/agent-evals)
- Node.js >= 20 and `pnpm` >= 10.4

```bash title="Install workspace dependencies"
pnpm install
```

## 1. Design the problem

Before scaffolding, decide:

- **Domain**: for v0.x, use `foo-bar`
- **Tier**: `tier-1` (single skill), `tier-2` (multi-step), or `tier-3` (cross-system). See the [tier definitions on the homepage](https://decbench.ai/#evaluation-design).
- **Starting state**:
  - Broken/incomplete: infrastructure boots with defects the agent must diagnose and fix
  - Clean/greenfield: infrastructure is healthy and the agent builds from scratch

Define success in concrete, pass/fail terms. Good evals produce deterministic outcomes, not subjective judgments.

## 2. Scaffold the scenario

Once you know what you are building, the CLI generates all required files and directories.

```bash title="Scaffold a new scenario"
dec-bench create \
  --name <my-scenario> \
  --domain <my-domain> \
  --tier tier-1
```

| Flag | Required | Default | Description |
|------|----------|---------|-------------|
| `--name` / `-n` | yes | | Scenario ID, used as directory name and JSON id |
| `--domain` / `-d` | yes | | Business domain (`foo-bar` for v0.1) |
| `--tier` / `-t` | no | `tier-1` | Difficulty tier (`tier-1`, `tier-2`, `tier-3`) |
| `--harness` | no | `base-rt` | Evaluation harness profile |
| `--dir` | no | `scenarios` | Root directory for scenario output |

This generates:

<Files>
  <Folder name="scenarios/<my-scenario>" defaultOpen>
    <Folder name="assertions" defaultOpen>
      <File name="correct.ts" />
      <File name="functional.ts" />
      <File name="performant.ts" />
      <File name="production.ts" />
      <File name="robust.ts" />
    </Folder>
    <Folder name="init" defaultOpen>
      <File name="postgres-setup.sql" />
    </Folder>
    <Folder name="prompts" defaultOpen>
      <File name="baseline.md" />
      <File name="informed.md" />
    </Folder>
    <File name="scenario.json" />
    <File name="supervisord.conf" />
  </Folder>
</Files>

| Path | Purpose |
|------|---------|
| `assertions/` | One TypeScript file per gate (functional, correct, robust, performant, production). Each exports named assertion functions that return pass/fail results. See [step 5](#5-write-gate-assertions) below and [Writing Assertions](/docs/add-eval/writing-assertions) for details. |
| `init/` | Shell scripts and SQL files that run before the agent starts. Use these to seed data, create schemas, or introduce intentional defects. |
| `prompts/` | Two markdown files, one per persona. `baseline.md` gives the agent minimal guidance; `informed.md` provides explicit technical context. |
| `scenario.json` | Metadata: scenario ID, domain, tier, harness, task descriptions, and tags. This is how the CLI and registry identify the scenario. |
| `supervisord.conf` | Declares which services ([Postgres](https://www.postgresql.org/), [ClickHouse](https://clickhouse.com/), [Redpanda](https://redpanda.com/)) start inside the container and in what order. Managed by [supervisord](http://supervisord.org/). |

All files are pre-populated with the right structure and placeholder comments.

## 3. Write the persona prompts

Each scenario has two prompts in `prompts/`, one per persona. The persona is an independent variable in the benchmark: every scenario is run separately with each prompt, and the results are compared to measure how much the agent's performance depends on the quality of guidance it receives.

- **`baseline.md`**: plain language, no tool names or implementation hints. Tests what the agent figures out on its own.
- **`informed.md`**: names specific tools, sets explicit targets, provides technical constraints. Tests whether domain knowledge changes the outcome.

```markdown title="prompts/baseline.md"
I have a bunch of CSV files that need to go into ClickHouse.
Some of them have messy data -- weird dates, missing values.
Can you get it all loaded into a clean table?
```

```markdown title="prompts/informed.md"
Ingest five CSV files from /data/csv/ into a single ClickHouse
table `analytics.events`. Handle DD/MM/YYYY dates, mixed null
representations (N/A, null, empty), duplicate header rows
mid-file, and trailing delimiters. Target schema: event_id
String, event_ts DateTime, user_id String, event_type String,
value Float64 (nullable values should be 0).
```

Both prompts should target the same outcome and the baseline should be solvable.

For more details, see [Adding Persona Prompts](/docs/add-eval/adding-persona-prompts).

## 4. Set up infrastructure and seed data

Services run inside the scenario container via `supervisord.conf`. Init scripts in `init/` set up their initial state.

```ini title="supervisord.conf example"
[program:postgres]
command=/usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/data
autostart=true
autorestart=false

[program:clickhouse]
command=/usr/bin/clickhouse-server --config-file=/etc/clickhouse-server/config.xml
autostart=true
autorestart=false
```

Connection strings are exported as environment variables (`$POSTGRES_URL`, `$CLICKHOUSE_URL`, etc.) so the agent and assertions can use them directly.

Seed data using init scripts in `init/`. These run after services are ready but before the agent starts. They can be SQL files, shell scripts, or anything executable.

```sql title="init/postgres-setup.sql (from foo-bar-cross-system-reconciliation)"
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE app.transactions (
  id SERIAL PRIMARY KEY,
  customer_id TEXT NOT NULL,
  amount NUMERIC(10, 2) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

INSERT INTO app.transactions (customer_id, amount, created_at) VALUES
  ('c001', 10.00, '2026-01-15T09:00:00Z'),
  ('c002', 25.50, '2026-01-15T09:05:00Z'),
  ('c003', 33.33, '2026-01-15T09:10:00Z'),
  ('c004', 47.99, '2026-01-15T09:15:00Z'),
  ('c005', 52.00, '2026-01-15T09:20:00Z');
```

For broken/incomplete starts, use init scripts to introduce defects (misconfigured connections, missing indexes, schema drift). For clean/greenfield starts, provide healthy infrastructure and realistic source data.

Seed deterministic data, export connection settings via environment variables, and avoid hidden state that makes runs non-reproducible.

For more details, see [Adding Multiple Services](/docs/add-eval/adding-multiple-services).

## 5. Write gate assertions

Gates are evaluated sequentially: a scenario must pass all assertions in one gate before the next gate runs. The framework includes core assertions that run for every scenario (e.g. `process_exits_clean`, `no_unhandled_errors` in the functional gate). Your scenario's assertion files in `assertions/` add scenario-specific checks on top of these.

For inspiration, browse the [assertions in existing scenarios](https://github.com/514-labs/agent-evals/tree/main/scenarios). Each scenario's `assertions/` directory shows real examples of gate checks.

| Gate | Question it answers | Typical checks |
|------|-------------------|----------------|
| Functional | Did it run? | Process exits cleanly, target table exists |
| Correct | Is the output right? | Row counts, checksums, schema/type expectations |
| Robust | Does it handle edge cases? | Nulls, duplicates, idempotent reruns |
| Performant | Is it fast enough? | Query latency, pipeline runtime thresholds |
| Production | Would you ship this? | No hardcoded secrets, tests present |

Each assertion returns an `AssertionResult` with `passed`, plus optional `message` and `details` fields.

```ts title="assertions/functional.ts"
import type { AssertionContext, AssertionResult } from "@dec-bench/eval-core";

export async function target_table_exists(ctx: AssertionContext): Promise<AssertionResult> {
  const result = await ctx.clickhouse.query({
    query: "SELECT count() AS n FROM system.tables WHERE database = 'analytics' AND name = 'events'",
    format: "JSONEachRow",
  });
  const rows = await (result as any).json();
  const count = Number(rows[0]?.n ?? 0);
  return {
    passed: count === 1,
    message: count === 1 ? "Target table exists." : `Expected 1 table, got ${count}.`,
    details: { expected: 1, actual: count },
  };
}
```

One check per function, actionable failure messages, deterministic results.

For more details, see [Writing Assertions](/docs/add-eval/writing-assertions).

## 6. Select a harness

The harness determines what tools are available to the agent. Like the persona, the harness is a variable in the benchmark: the same scenario can be run with different harnesses to measure how tool availability affects performance. Use an existing profile when possible.

| Harness | What it installs |
|---------|-----------------|
| `base-rt` | Base infrastructure (ClickHouse, Redpanda, Postgres) with Python, Node.js, database CLIs |
| `classic-de` | dbt-core, dbt-postgres, dbt-clickhouse, apache-airflow, pyspark |
| `olap-for-swe` | [MooseStack](https://www.moosestack.com/), an agent harness for data engineering over ClickHouse, Postgres, and Redpanda |

## 7. Register the scenario

The `scenario.json` file is how the CLI and the [scenario registry](https://decbench.ai) identify and describe your scenario. The scaffold step pre-fills `id`, `domain`, `tier`, and `harness` from the flags you passed. Complete the remaining fields: `title`, `description`, `tasks`, and `tags`.

```json title="scenario.json"
{
  "id": "foo-bar-csv-ingest",
  "title": "Foo Bar CSV Ingest",
  "description": "Load five messy CSV files into clean ClickHouse tables.",
  "tier": "tier-1",
  "domain": "foo-bar",
  "harness": "base-rt",
  "tasks": [
    {
      "id": "ingest-csvs",
      "description": "Create a ClickHouse table and load all five CSV files.",
      "category": "ingestion"
    }
  ],
  "personaPrompts": {
    "baseline": "prompts/baseline.md",
    "informed": "prompts/informed.md"
  },
  "tags": ["csv", "ingestion", "data-cleaning", "type-coercion"]
}
```

See `packages/scenarios/src/types.ts` for the full schema contract.

## 8. Run and validate locally

Test with a single agent/harness/persona combination. The benchmark will run all combinations once the scenario is published.

```bash title="Run the scenario"
dec-bench build --scenario <my-scenario>
dec-bench run --scenario <my-scenario>
```

Verify the output:

- Gate-level pass/fail and scores are present
- Failures are actionable from assertion messages
- Results are stable across repeated runs

## PR checklist

- Prompts are specific, scoped, and testable
- All five gate assertion files exist and export valid functions
- Deterministic seed data is included
- No hardcoded secrets or credentials
- Scenario metadata matches allowed `tier`, `domain`, and `harness` values

```bash title="Validation checks"
pnpm --filter @dec-bench/scenarios check-types
pnpm --filter @dec-bench/scenarios lint
pnpm lint
```
